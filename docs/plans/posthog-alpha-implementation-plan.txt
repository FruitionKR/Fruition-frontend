## 0. 요약

2026-10-22 검토 반영: 실패·성공 되돌리기 키 분리, 서버 terminal 결과 상호 배제, D15 행동 마감/D18 후속 관찰 분리, 코호트 밖 팀원의 최초 편입 이력 포함, 질문 접수 시각으로 24h 판정, AI 스킬 생성 원자 기록. 원문의 근거 답변·지표 2 분모·자동 편입 포함 정의를 기본값으로 유지하고 변경안은 보조 분석으로만 사용합니다.

1. **핵심 지표 4개는 전부 서버 이벤트로만 계산합니다.** 브라우저 이벤트는 광고 차단기, CSP, 탭 종료로 빠질 수 있으므로 보조 지표에만 씁니다.
2. **서버 전송은 서비스별 `analytics_outbox` 테이블을 거칩니다.** 제품 트랜잭션 안에서 이 테이블에 행을 넣고, 커밋된 뒤 relay가 PostHog `/batch`로 보냅니다. 커밋 후 전송과 재시도 시 동일 event_id 유지를 구현합니다. 수신 측은 즉시 exactly-once를 보장하지 않으므로 판정 쿼리에서도 event_id 기준으로 중복을 제거합니다. Document와 Access에는 outbox 선례가 있지만 실패 격리는 별도 구현·검증합니다. AI 스킬 생성도 생성 저장소에서 내구성 있게 기록해야 합니다.
3. **비동기 결과는 Document 결과 consumer에서 처리합니다.** AI 종료 이벤트에는 이미 `user_id`, `workspace_id`, `operation_id`, 결정적인 `event_id`가 실려 있습니다. Document의 결과 consumer가 이 값을 받아 분석 이벤트를 대신 기록합니다.
4. **원문의 통계·관찰창·인과 주장 중 그대로 실행하면 틀리는 것이 여럿입니다.** D7 창이 관찰 범위 밖에 있고, 웹 인용이 근거 답변에 섞이며, 결과를 본 뒤 관찰창을 확정하고, 상관관계를 인과로 해석하는 문제 등입니다. 3장에서 수정안과 함께 따로 정리했습니다.
5. **저장소별 작업을 분리합니다.** 사용자가 2026-10-22 서버·AI·인프라 수정을 명시적으로 허용하고 병렬 에이전트 구현을 요청했습니다. 각 서비스는 독립 작업 공간과 dev 대상 PR로 구현하며 이 저장소는 프론트 코드를 담당합니다.

### 2.4 AI

- **[확인]** 종료 이벤트 `_event()`에 `event_id = "{kind}:{run_id}:{status}"`, `run_id`, `status`, `workspace_id`, `user_id`, `operation_id`, `request`, `payload`, `error`가 들어 있습니다. 근거는 `pipeline/app/workers/task_worker.py` 966행과 `ingest_worker.py` 136행입니다.
- **[확인]** 실패 코드는 `provider_rate_limited`, `provider_unavailable`, `input_rejected`, `deadline_exceeded`, `cancelled`, `internal_error`이고 원문은 싣지 않습니다. 근거는 `app/core/failure_codes.py`입니다.

### 2.5 platform

- **[확인]** NetworkPolicy `aws-app-https`가 access-svc와 document-svc에 외부 443 egress를 허용합니다. 프론트 Pod는 Fargate라 NetworkPolicy가 적용되지 않습니다. 따라서 **서버에서 PostHog로 나가는 통신에 정책 변경은 필요 없습니다.**
- **[확인]** `k8s/overlays/aws/frontend.yaml`의 env는 ACCESS_CODE(secret), CSP_S3_ORIGIN 등입니다. 운영은 ALB가 같은 호스트에서 경로로 나누고, `SAME_ORIGIN_API=true`이면 Next rewrite가 없습니다.

## 3. 원문 수정 권고 (그대로 실행하지 말 것)

| # | 원문 | 문제 | 수정 권고 |
|---|---|---|---|
| R1 | 관찰 범위 `[t0, t0+7일)`, D7 = `[t0+7일, t0+8일)` | D7 창이 관찰 범위 밖에 있음 | 관찰 범위를 **`[t0, t0+8일)`**로 바꿈. "7일 내 활동 일수"는 `[t0, t0+7일)`로 따로 정의 |
| R2 | D1·D3·D7은 24h 롤링 창인데, "날짜는 Asia/Seoul로 자른다"고도 함 | 두 정의가 충돌함. 밤에 가입한 사람은 D1 창이 실질적으로 짧아짐 | **하나로 고정.** 권장은 롤링 24h 창(`t0 + n×24h`)이며 사람마다 공평함. Asia/Seoul 날짜는 "서로 다른 날짜 수"(지표 2, 활동 일수)에만 씀. PostHog 리텐션 인사이트는 프로젝트 시간대 기준 달력 구간이라 롤링 정의와 다름. 판정은 SQL로 하고, 리텐션 인사이트는 참고용으로만 씀 |
| R3 | 지표 2 "근거 답변을 받은 날이 3일 이상"(알파 전 기간) | 늦게 가입한 사람은 관찰 일수가 짧아 구조적으로 실패함(우측 검열) | 원문 분모(근거 답변 경험자)를 유지하되 **관찰 완료자**(t0 + 8일 ≤ 알파 종료)로 제한. 분자는 `[t0, t0+7일)` 안에서 근거 답변을 받은 Asia/Seoul 날짜 수 ≥ 3 |
| R4 | 보고 문장 "D%가 **3일 이상 다시 왔고**" | 지표는 첫날을 포함해 3일임. "다시 3일"이면 4일이 됨 | 문장을 "**서로 다른 3일 이상 근거 답변을 받았고**"로 고침 |
| R5 | "가입 당일 근거 답변 여부별 D3·D7 비교에서 차이가 나면 근거 답변이 재방문을 만든다고 말할 수 있다" | 인과 추론이 성립하지 않음. 의지가 강한 사람이 두 가지를 다 하는 선택 편향, 역인과, 수십 명 규모의 작은 표본 | **연관으로만 보고**하고 두 그룹 각각 n과 비율, Fisher 정확검정 또는 95% 신뢰구간을 붙임. "당일"은 달력일 대신 `[t0, t0+24h)`. 인과 주장이 필요하면 온보딩 무작위 배정이 필요하지만, 알파 규모로는 검정력이 부족해 이번에는 하지 않음 |
| R6 | 관찰창(72h)을 "D7에 1주차 `time_since_operation_sec` 분포의 90%로 확정" | ① 결과를 본 뒤 기준을 바꾸는 것이라 원문 1장 원칙과 모순. ② 1주차에 관찰된 되돌리기만 모이므로 긴 꼬리가 잘려 값이 낮게 나옴 | **72h를 사전 고정.** 1주차 분포는 24h/7d 민감도 분석으로 함께 보고하되 판정에는 쓰지 않음 |
| R7 | `has_citations`에 웹 인용 포함, 근거 답변 = `has_citations=true` | 웹 인용만 있는 답이 "쌓아 둔 지식"으로 집계돼 1-b와 지표 2가 부풀려짐. 서버는 웹 근거를 저장하지도 않음 | 속성을 `internal_citation_count`, `web_citation_count`로 나눔. 기본 판정은 원문대로 **`has_citations = true`**. 내부 근거 답변(`internal_citation_count > 0`)은 비교용 보조 지표로 병기하며 정의·목표값 합의 없이 기본값을 바꾸지 않음 |
| R8 | 1-a 분모 = 성공 편입이 1회 이상 있는 사람 | 알파 막바지에 처음 편입한 사람은 24시간 뒤 회수를 관찰할 시간이 없음 | 분모를 **첫 성공 편입 + 7일 ≤ 알파 종료인 사람**으로 제한. 분자는 첫 편입 후 7일 안에 묵은 회수가 있는 사람. 이 창은 보조 지표 "첫 성공 편입 → 첫 묵은 회수 중앙값 7일"과 맞춤 |
| R9 | 지표 3: AI 편집과 편입을 하나의 비율로 합침 | 자동 편입이 대부분이라 편입이 결과를 좌우함. 자동 편입은 사용자의 "신뢰 결정"도 아니고, 되돌리기가 적은 것은 몰라서일 수도 있음 | 핵심 3은 합산값과 함께 **AI 편집 / 수동 편입 / 자동 편입을 따로** 보고. 판정은 원문대로 AI 편집 + 모든 성공 편입으로 하고, 수동·자동 구분은 보조 분석 |
| R10 | "함께 되돌아간 작업"을 따로 표시만 함 | 유지율 분자에서 어떻게 처리할지 정의가 없음 | 신뢰성(롤백률)에는 지목 + 연쇄 모두 "되돌려짐"으로 셈. 신뢰(핵심 3)는 지목된 작업만 셈. 둘 다 보고 |
| R11 | 롤백 시각 기준이 불명확함(이벤트는 완료 시점에 발송) | 재작성이 길어지면 72h 경계에서 판정이 바뀜 | 판정 기준 시각을 **되돌리기 요청 시각**(`restore_requested_at` 속성)으로 고정. 이벤트 timestamp는 완료 시각 |
| R12 | 소규모 비율 | 표본 수십 명이라 비율이 크게 흔들림 | 모든 비율에 분자/분모와 **Wilson 95% 신뢰구간**을 붙임. 목표 달성 여부는 사전 등록한 점추정 기준으로 판정 |
| R13 | 편입 선택창 이탈: "편입을 시작하지 않은" | 편입 **시작** 이벤트가 명세에 없음 | `wiki_ingest_requested`(서버, enqueue 커밋 후)를 추가 |
| R14 | 채팅 내보내기 완주 | 내보내기와 편입이 별도 요청이라 `export_id`를 이어 줄 길이 없음 | 계약 C6 추가(6장) |
| R15 | `edit_diff_viewed`("펼쳤을 때")와 "diff 확인 후 수락" | 현재 UI에 펼치기 동작이 없음(2.1 표) | 이벤트를 **`edit_review_shown`**(제안 검토가 처음 표시됐을 때)으로 바꾸고, "diff 확인 후 수락" 지표는 뺌. 검토 없이 적용하는 경로(`openMarkdownEditAsNewDocument` 등)가 생기면 그때 다시 도입 |
| R16 | 봇 필터를 모든 인사이트에 적용 | PostHog의 `$virt_is_bot`은 브라우저가 아닌 SDK 이벤트를 봇으로 분류할 수 있음 [문서] | 봇 필터는 **`event_source = frontend` 이벤트에만** 적용. 서버 이벤트에는 걸지 않음 |
| R17 | 원문 HogQL 예시 | 코호트, 내부 계정, `schema_version` 필터와 event_id 중복 제거가 빠짐. 지표 2는 t0 기준 창이 없음 | 12장의 수정 쿼리를 사용 |
| R18 | "알파 시작 후 7일 안에 가입" = 관찰 완료 | D14 경계(포함인지)가 정의되지 않음 | 알파 기간을 `[D0 00:00 KST, D15 00:00 KST)`로 명시. 관찰 완료 조건 `t0 + 8일 ≤ D15 00:00` → 가입 마감 **D6 24:00** |
| R19 | 업로드 → 편입 시간 − `duration_sec` = 망설임 | 자동 편입이면 망설임이 0에 가깝고, 실패 후 재시도는 섞임 | `trigger`(auto/manual) 속성을 추가하고 **manual만** 망설임 분석에 씀 |
| R20 | `restore_count` = 되돌린 작업 수 | 기존 API의 `restore_count`(페이지 수)와 의미가 충돌함 | 분석 속성 이름을 **`restored_operation_count`**로 바꿈 |

## 4. 공통 이벤트 계약 (schema_version = 1)

### 4.1 envelope

**[제안]** 서버와 프론트가 같은 envelope을 씁니다.

| 필드 | 규칙 |
|---|---|
| `distinct_id` | `user_<hex>`(Access users.id). 이메일과 닉네임은 쓰지 않음 |
| `uuid` | **서버는 논리 키로 만든 UUIDv5.** NAMESPACE_URL=`6ba7b811-9dad-11d1-80b4-00c04fd430c8`, 이름은 `fruition.analytics.v1:{event}:{논리키}`. 프론트의 개별 행동은 UUIDv4. PostHog는 uuid, event, timestamp, distinct_id가 모두 같은 이벤트를 결국 중복 제거하지만 즉시 지우지는 않음 [문서] |
| `timestamp` | 실제 발생 시각(UTC ISO-8601). outbox 행에 저장하고 재전송해도 바꾸지 않음. 같아야 중복 제거가 됨 [문서] |
| `properties.event_id` | `uuid`와 같은 값의 문자열. 쿼리에서 중복 제거할 때 씀 |
| `properties.event_source` | `frontend`, `access_server`, `document_server`, `worker`. AI 스킬 생성은 `worker`, Document가 반영하는 AI 비동기 결과는 `document_server` |
| `properties.environment` | `local`, `staging`, `production` |
| `properties.schema_version` | `1` |
| `properties.app_version` | 배포 커밋 SHA. 이미지 태그에서 주입 |
| `properties.$groups` | `{"workspace": "<id>"}`. 작업의 **대상** 워크스페이스. 가입 이벤트와 워크스페이스가 없는 페이지뷰에서는 생략 |
| `properties.workspace_id` | 대상 workspace의 일반 문자열 속성. 유료 Group analytics 활성화 없이도 workspace별로 조회할 수 있도록 `$groups`와 함께 보냄. 대상이 없는 개인 스킬·가입·페이지뷰에서는 생략 |

**[제안] 논리 키**

| 이벤트 | 논리 키 |
|---|---|
| `user_signed_up` | `user_id` |
| `member_invited` | `invitation_id`. 재발송은 같은 키라 1건 |
| `member_joined` | `invitation_id` |
| `document_uploaded` | `document_id` |
| `wiki_ingest_requested` / `wiki_ingest_completed` | `ingest_id`(= ingest run_id) |
| `pdf_convert_completed` | `conversion_id` |
| `query_answered` / `query_failed` | `query_id`. 이벤트 이름이 달라 UUID도 다르므로 서버의 질문별 terminal receipt에서 성공·실패 상호 배제를 보장 | 
| `ai_edit_proposed` | `proposal_id` |
| `ai_edit_decided` | `proposal_id` |
| `ai_operation_rolled_back` | 성공은 원래 `operation_id`당 최초 1건. 실패는 `restore_attempt_id`(되돌리기 작업 ID)당 1건으로 별도 키 사용. 실패가 성공 기록을 막아서는 안 됨 |

| `skill_created` | `skill_id` |

### 4.2 값 규칙

원문 4장을 그대로 따르고, 아래를 추가합니다.

- `failure_reason` 매핑 **[제안]**

  | AI 실패 코드 | `failure_reason` |
  |---|---|
  | `provider_rate_limited`, `provider_unavailable` | `provider_error` |
  | `deadline_exceeded` | `timeout` |
  | `input_rejected` | `validation` |
  | `internal_error`, `task_failed` | `internal_error` |
  | `cancelled` | 이벤트를 보내지 않음 |

  Document 쪽 예외는 `permission`, `storage_error`로 매핑하고, 그 밖은 `unknown`으로 둡니다.
- `edit_type` 매핑 **[제안]**

  | `AgentTurnEdit` | `edit_type` |
  |---|---|
  | `insert_after` | `append` |
  | `replace` + `whole_document` | `rewrite` |
  | `replace` + `selection` 또는 `current_section` | `replace` |
  | 그 밖 | `other` |

- `method`: `email`(PROVIDER_LOCAL), `google`, `naver`, `kakao`
- `role`: `owner`, `member`(enum 소문자)

## 7. 전송 배선

### 7.1 프론트 SDK (posthog-js, 이 저장소에서 할 일)

**설치와 초기화 [제안]**

- `web/package.json`에 `posthog-js`를 추가합니다.
- `src/shared/lib/analytics/` 아래에 다음을 둡니다.
  - `client.ts`: `init`, `capture`, `identify`, `reset` 래퍼
  - `sanitize.ts`: URL과 속성 정리
  - `events.ts`: 이벤트 이름과 속성 타입. 허용 목록 역할을 함
- `AnalyticsProvider`를 `Providers` 맨 바깥에 둡니다.
- 토큰은 **런타임 서버 env**로 받고 프론트 수집 host는 US 공식 도메인으로 고정합니다. `RootLayout`(이미 force-dynamic)에서 `process.env.POSTHOG_PROJECT_TOKEN`, `ANALYTICS_ENVIRONMENT`, `APP_VERSION`을 읽어 Providers에 prop으로 넘깁니다.
  - 이유: 운영 Dockerfile에 빌드 ARG가 없고, `NEXT_PUBLIC_*`는 빌드할 때 고정되기 때문입니다 [확인].
  - 공식 가이드는 `instrumentation-client.ts` + `NEXT_PUBLIC_*` 방식입니다 [문서]. 이 방식을 쓰면 빌드 ARG를 추가해야 합니다.
- 토큰이 비어 있으면 초기화하지 않습니다. 이것이 롤백 스위치입니다.

**init 옵션 [문서] 기준 [제안] 값**

```ts
posthog.init(token, {
  api_host: "https://us.i.posthog.com",
  defaults: "2026-08-30",
  autocapture: false,
  capture_pageview: false,          // 정리된 URL로 수동 capture
  capture_pageleave: false,
  capture_dead_clicks: false,
  capture_heatmaps: false,
  capture_performance: false,
  capture_exceptions: false,
  disable_surveys: true,
  advanced_disable_flags: true,
  disable_external_dependency_loading: true,
  disable_session_recording: true,
  person_profiles: "identified_only",
  mask_all_text: true,
  mask_all_element_attributes: true,
  property_denylist: ["$referrer", "$initial_referrer", "$referring_domain", "$initial_referring_domain"],
  before_send: sanitizeEvent,       // 이벤트별 허용 속성 외 제거 + $current_url/$pathname 템플릿화
  prepare_external_dependency_script: (s) => { s.nonce = nonce; return s; },
  session_recording: {
    maskAllInputs: true,
    maskTextSelector: "*",
    maskCapturedNetworkRequestFn: () => null,
  },
});
```

현재 원격 기능 평가와 외부 확장 로딩은 사용하지 않으므로 `advanced_disable_flags`와 `disable_external_dependency_loading`을 켭니다. 리플레이를 후속 활성화할 때 해당 옵션과 snapshot 허용 목록을 함께 검토하고 staging에서 마스킹을 다시 검증합니다.

**URL 정리 [제안]**

| 실제 경로 | 보내는 값 |
|---|---|
| `/invitations/{token}` | `/invitations/:token` |
| `/oauth/callback`, `/reset-password`, `/signup/verify` | 쿼리 전체 제거 |
| `/home?page=..&doc=..&tree=..` | `/home` + `$screen` 속성(`page`/`document`/`tree`/`graph`…). ID는 URL에 남기지 않고 필요하면 별도 속성으로 보냄 |
| 그 밖 | 해시와 쿼리 제거 |

`$current_url`은 `origin + 템플릿 경로`만 남깁니다.

**identify, reset, group [제안]**

- `useMe()`가 성공하면 `posthog.identify(me.id)`를 호출합니다. person 속성은 넣지 않습니다(이메일, 이름 금지).
- 이미 식별된 다른 ID가 있으면 먼저 `reset()`을 부르고 identify합니다. 계정 전환 대응입니다.
- `reset()`은 세 곳에서 부릅니다.
  - `useSignOut.signOut`
  - `setSessionExpiredHandler`에 등록된 처리기
  - 회원 탈퇴 `clearFruitionStorage` 경로
- 워크스페이스를 고르거나 바꿀 때 `posthog.group("workspace", id)`를 부릅니다. 웹 SDK에서는 이후 세션 이벤트가 이 그룹에 묶입니다 [문서].
- 다만 이벤트의 대상 워크스페이스가 현재 선택과 다를 수 있으면 `$groups`를 명시합니다. 예: 다른 워크스페이스 문서의 인용.
- 로그인 전 `$pageview`는 `identified_only` 설정 때문에 익명으로 남습니다.

**CSP (`contentSecurityPolicy.ts`, 프론트 변경) [제안]**

- `connect-src`에 `https://us.i.posthog.com`, `https://us-assets.i.posthog.com`을 추가합니다.
- `worker-src 'self' blob: data:`를 추가합니다(리플레이용).
- `script-src`는 기존 `'strict-dynamic'` + nonce 주입(`prepare_external_dependency_script`)으로 리플레이 스크립트를 받습니다. **staging에서 CSP 보고(`/csp-report`)로 확인합니다.**
- 공식 권고는 `*.posthog.com` 와일드카드입니다 [문서]. 범위를 좁힌 위 목록이 깨지면 와일드카드로 바꿉니다.

**리버스 프록시**

알파에서는 쓰지 않습니다 [제안]. 운영 ALB가 경로로 나누고 `SAME_ORIGIN_API`에서 rewrite가 꺼져 있어, 프록시를 넣으려면 ALB 규칙 추가가 필요합니다. 차단기로 빠지는 것은 프론트 보조 지표뿐이고 핵심 지표는 서버 이벤트입니다. 차단율이 문제로 보이면 PostHog managed reverse proxy [문서]를 검토합니다.

**호출 래퍼 규칙**

- 모든 capture는 try/catch로 감싸고, 실패해도 무시합니다(제품 영향 없음).
- 재렌더링 중복은 `useRef`로 "열림당 1회"를 지킵니다.

### 7.2 서버 outbox (Document·Access 담당자 요구사항)

**테이블 [제안]**

```sql
analytics_outbox(
  uuid uuid PRIMARY KEY,               -- 논리 키 UUIDv5
  event text NOT NULL,
  distinct_id text NOT NULL,
  occurred_at timestamptz NOT NULL,    -- = PostHog timestamp
  properties jsonb NOT NULL,           -- 허용 목록 통과값만
  attempts int NOT NULL DEFAULT 0,
  next_attempt_at timestamptz NOT NULL DEFAULT now(),
  last_error_code text,
  sent_at timestamptz
);
```

insert는 `ON CONFLICT (uuid) DO NOTHING`입니다. 이것이 1차 중복 제거입니다.

**기록**

- 제품 트랜잭션 안에서 `AnalyticsRecorder.record(...)`를 호출합니다.
- Access는 `EmailChangeNotificationListener`처럼 `@EventListener` + `Propagation.MANDATORY`를 씁니다.
- Document는 `AiTaskResultApplier` 각 apply의 receipt-first 분기 안에서 직접 호출합니다.

**Relay**

- `AiCommandOutboxPublisher`처럼 `@Scheduled` + `FOR UPDATE SKIP LOCKED`로 최대 100건을 가져옵니다.
- `POST https://us.i.posthog.com/batch/`로 보내며, body는 `api_key`와 `batch[]`(uuid, event, distinct_id, timestamp, properties)입니다 [문서].
- 성공하면 `sent_at`을 기록합니다. 실패하면 `attempts++`, 지수 백오프(최대 1h), 24회가 넘으면 `dead`로 두고 경고 로그를 남깁니다.
- `sent_at` 행은 7일 뒤 삭제합니다.
- 클러스터가 절전 중이어도 행은 남았다가 깨어난 뒤 발송됩니다.

**SDK 대신 HTTP를 쓰는 이유**

- 공식 Java SDK(`com.posthog:posthog-server`) 문서에는 uuid와 timestamp 지정 방법이 없습니다 [문서].
- 결정적인 uuid와 원래 발생 시각을 보장해야 중복 제거가 되므로, HTTP를 직접 부르는 것이 확실합니다.
- 1주 스파이크로 SDK가 두 값을 지원한다고 확인되면 SDK로 바꿀 수 있습니다.

**실패 격리**

- insert는 단순 행 추가라 실패 가능성은 낮습니다. 그래도 같은 트랜잭션이라 insert가 실패하면 제품 작업도 롤백됩니다. 원문의 "분석 실패가 제품 실패가 되면 안 된다"를 충족하지 못하므로, 아래 실패 격리 검증은 선택 사항이 아닌 구현 게이트입니다.
- 완화책
  - `ANALYTICS_ENABLED=false`이면 기록을 건너뜁니다.
  - properties는 기록 전에 직렬화 검증을 합니다.
  - 테이블에 FK를 두지 않습니다.
  - 원문의 제품 실패 격리 요구를 충족하려면 insert 실패를 JDBC SAVEPOINT 등으로 격리하는 방식을 기본 설계로 검증해야 합니다. 단순 예외 catch만으로 rollback-only가 해제된다고 가정하지 않습니다. 제품 저장 성공·분석 기록 실패를 재현하는 통합 테스트를 통과해야 적용하며, 누락 이벤트는 운영 지표와 경고로 추적합니다.

**중복 제거 3중 구조**

1. outbox PK
2. PostHog uuid 기반 결국 중복 제거 [문서]. 즉시가 아니고 보장도 약하다고 명시돼 있습니다.
3. **모든 판정 쿼리에서 `event_id`로 GROUP BY**

**논리 event_id와 "재시도는 새 행동이 아니다"**

- AI consumer 재전달은 `ai_task_result_receipts`에서 한 번 막히고, 같은 논리 키라 outbox에서 다시 막힙니다.
- 사용자가 새로 재시도하면 새 run_id라 새 이벤트입니다.

## 8. 본문·개인정보·URL·리플레이 보호

- **허용 목록 방식.** 서버는 이벤트 타입별 record 클래스, 프론트는 `before_send`로 정의된 속성만 통과시킵니다. 질문·답변·본문·파일명·워크스페이스명·이메일·토큰·오류 원문은 타입 단계에서 넣을 수 없게 합니다.
- **AI 실패 정보**는 이미 코드만 오므로(2.4) 그 코드를 매핑해 씁니다.
- **리플레이**
  - SDK에서 `maskAllInputs`와 `maskTextSelector:"*"`, 네트워크 요청은 `maskCapturedNetworkRequestFn → null`로 막습니다.
  - 편집기(Milkdown), 채팅 스레드, 원문 미리보기(iframe blob), 그래프 라벨 컨테이너에는 `ph-no-capture` 클래스를 붙입니다. 블록 처리돼 크기만 보입니다 [문서].
  - 프로젝트 설정에서는 네트워크 payload와 콘솔 로그 캡처를 끕니다(9장).
- **IP**: 프로젝트의 클라이언트 IP 폐기 설정을 켤지 결정해야 합니다(16장).
- **법무**: PostHog US로 데이터가 국외 이전되고 리플레이도 수집되는데, 처리방침 제7조와 제11조가 아직 자리표시자입니다 [확인]. **처리방침 확정 전에는 리플레이를 끈 채 알파를 시작**하는 것을 권합니다. 분석 이벤트는 가명 ID라도 고지가 필요합니다.
- **본문 누출 검사**
  - CI에서 이벤트 builder 테스트로 금지 키를 검사합니다.
  - staging에서 PostHog SQL `SELECT DISTINCT arrayJoin(JSONExtractKeys(properties))`로 속성 키 목록을 뽑아 허용 목록과 대조합니다.

## 12. 판정 쿼리 (HogQL, staging에서 손 집계와 대조한 뒤 사용)

- 문법은 [가정]입니다. `properties.x`로 접근하는 방식은 [문서]로 확인했지만, `IN COHORT`, 배열 JSON 추출, 시간대 함수는 staging에서 실제로 확인해야 합니다.
- `{{alpha}}`는 알파 참여자 코호트 ID입니다.
- `D15`는 제품 행동 포함 마감, `followup_end`는 D18 이후 관찰 마감입니다. 문서 최초 편입 이력은 분석 사용자 코호트와 무관하게 대상 workspace 전체에서 조회합니다.
- Document는 `query_answered.cited_document_first_ingested_at`에 원문 문서 ID → 최초 성공 편입 UTC 시각 객체를 제공합니다. 이 값은 같은 workspace의 전체 사용자와 기존 변환 문서 계보에서 조회하며, 알파 이전 문서도 포함합니다. `wiki_ingest_completed.first_success_ingested_at`도 동일한 기준입니다. 새 이벤트의 발생 시각으로 과거 편입 시각을 덮어쓰지 않습니다.
- `D15`는 `toDateTime('YYYY-MM-DD 00:00:00','Asia/Seoul')` 상수로 바꿉니다.

**공통 CTE: 중복 제거된 기본 이벤트**

```sql
WITH all_events AS (
  SELECT properties.event_id AS event_id,
         any(event) AS event, any(person_id) AS person_id, min(timestamp) AS ts,
         any(properties) AS p
  FROM events
  WHERE properties.environment = 'production'
    AND properties.event_id IS NOT NULL AND properties.event_id != ''
    AND toInt(properties.schema_version) = 1
    AND timestamp < {{followup_end}}
  GROUP BY event_id
),
base AS (SELECT * FROM all_events WHERE person_id IN COHORT {{alpha}} AND ts < {{D15}})
```

**t0 (가입 시각)**

```sql
t0 AS (SELECT person_id, min(ts) AS t0 FROM base WHERE event = 'user_signed_up' GROUP BY person_id)
```

**1-a 묵은 지식 회수 (R8)**

```sql
first_ingest_doc AS (
  SELECT JSONExtractString(p, 'workspace_id') AS workspace,
         JSONExtractString(p, 'document_id') AS doc,
         min(coalesce(parseDateTimeBestEffortOrNull(JSONExtractString(p, 'first_success_ingested_at')), ts)) AS ingested_at
  FROM all_events WHERE event = 'wiki_ingest_completed' AND JSONExtractString(p,'status') = 'succeeded'
  GROUP BY workspace, doc),
first_ingest_person AS (
  SELECT person_id, min(ts) AS fi FROM base
  WHERE event = 'wiki_ingest_completed' AND JSONExtractString(p,'status') = 'succeeded'
  GROUP BY person_id),
cited AS (
  SELECT person_id, ts, JSONExtractString(p, 'workspace_id') AS workspace,
         parseDateTimeBestEffort(JSONExtractString(p, 'query_requested_at')) AS requested_at,
         arrayJoin(JSONExtract(p, 'cited_document_ids', 'Array(String)')) AS doc,
         parseDateTimeBestEffortOrNull(JSONExtractString(p, 'cited_document_first_ingested_at', doc)) AS canonical_ingested_at
  FROM base WHERE event = 'query_answered' AND JSONExtractBool(p,'has_citations')),
eligible AS (SELECT person_id, fi FROM first_ingest_person WHERE fi + INTERVAL 7 DAY <= {{D15}})
SELECT countDistinctIf(e.person_id, c.matched = 1) AS numerator, count(DISTINCT e.person_id) AS denominator
FROM eligible e
LEFT JOIN (
  SELECT DISTINCT c.person_id, c.ts, c.requested_at, 1 AS matched FROM cited c
  LEFT JOIN first_ingest_doc f ON f.workspace = c.workspace AND f.doc = c.doc
  WHERE (c.canonical_ingested_at IS NOT NULL OR f.doc != '')
    AND c.requested_at >= coalesce(c.canonical_ingested_at, f.ingested_at) + INTERVAL 24 HOUR) c
  ON c.person_id = e.person_id AND c.requested_at >= e.fi AND c.requested_at < e.fi + INTERVAL 7 DAY
```

**1-b 지식 결합 비율**

```sql
SELECT countIf(length(arrayDistinct(JSONExtract(p,'cited_document_ids','Array(String)'))) >= 2) AS numerator, count() AS denominator
FROM base WHERE event = 'query_answered' AND JSONExtractBool(p,'has_citations')
```

**지표 2 (R1, R3)**

```sql
SELECT countIf(days >= 3) AS numerator, count() AS denominator FROM (
  SELECT t.person_id, uniqIf(toDate(b.ts, 'Asia/Seoul'),
           b.event = 'query_answered' AND JSONExtractBool(b.p,'has_citations')
           AND b.ts >= t.t0 AND b.ts < t.t0 + INTERVAL 7 DAY) AS days
  FROM t0 t LEFT JOIN base b ON b.person_id = t.person_id
  WHERE t.t0 + INTERVAL 8 DAY <= {{D15}}
  GROUP BY t.person_id HAVING days > 0)
```

분모는 원문대로 관찰 완료자 중 근거 답변 경험자(`HAVING days > 0`)입니다. 전체 가입자 대비 비율은 별도의 활성화 지표로만 보고합니다.

**지표 3 AI 결과 유지율 (R6, R9~R11)**

- 대상: `ai_edit_decided(accepted)`의 `operation_id`와, `wiki_ingest_completed(succeeded)` 모든 `operation_id`(auto/manual 모두 포함). 작업 시각 `op_ts`.
- 조건: `op_ts < D15` AND `op_ts + 72h ≤ followup_end`인 작업만 분모에 넣습니다.
- 분자: 후속 관찰까지 포함한 `all_events`의 `ai_operation_rolled_back(status = succeeded)` 중에서
  - 지목 기준: `operation_id = 대상`이고 `restore_requested_at < op_ts + 72h`인 것이 **없는** 작업
  - 연쇄 포함 기준: `has(cascaded_operation_ids, 대상)`까지 넣어 같은 방식으로 따로 계산
- 결과는 유형별(ai_edit / 수동 편입 / 자동 편입)로 `GROUP BY`합니다.

**D1, D3, D7 (R2)**: 롤링 24h 창 `[t0 + n일, t0 + (n+1)일)`에 핵심 행동이 있으면 1로 봅니다. 분모는 `t0 + (n+1)일 ≤ D15`인 사람입니다.

**재방문 보조 비교 (R5)**: 첫 24h 근거 답변 여부 두 그룹의 D3·D7 비율, 각 n, Fisher p값을 **연관으로만** 표기합니다.

**첫 가치 도달 시간**: 사람별로 각 단계의 `min(ts)` 차이를 구해 `median`과 도달률(도달 / 관찰 완료자)을 함께 냅니다. 업로드 → 편입 망설임은 `trigger = manual`인 경우에만 계산합니다.

## 17. 미결정 사항 (알파 전 확정)

1. 핵심·보조 목표값은 원문 제안값을 기본으로 삼고 알파 전에 확정. 정의 변경안은 별도 보조 분석이며 합의 없이 판정에 대입하지 않습니다.
2. 알파 기간 경계(D0, D15 00:00 KST)와 초대 마감 D6.
3. 지표 2 분모는 관찰 완료자 중 근거 답변 경험자로 유지. 전체 가입자 대비 비율은 별도 활성화 지표.
4. 지표 3은 자동 편입을 포함한 모든 성공 편입과 수락된 편집으로 유지. 회의록 포함 여부만 별도 결정.
5. 일부 수락(C4)을 수락으로 볼지(권고: 1개 이상 수락이면 accepted + hunk 비율 기록). `openMarkdownEditAsNewDocument`(새 문서로 만들기)를 수락으로 볼지.
6. 658129를 production 전용으로 쓸지, environment 필터로 함께 쓸지.
7. Group analytics 유료 add-on 사용 여부. 쓰지 않으면 `$groups` 대신 `workspace_id` 일반 속성으로 분류합니다.
8. 처리방침 제7조와 제11조 확정, 리플레이 시작 시점, 클라이언트 IP 폐기 여부.
9. 서버 전송을 HTTP batch로 할지, Java SDK(uuid·timestamp 지원 확인 후)로 할지.
10. C8: AI 스킬 응답에 scope와 생성자가 있는지. 없으면 AI 저장소 요구사항이 생깁니다.
11. `pages_changed`가 changedResourceCount와 같은 의미인지, 어시스턴트 메시지 `run_id`가 query `request_id`와 같은지 확인.
12. 판정일(D18)과 보고 문장 수정본(R4).
